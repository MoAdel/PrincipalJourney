# Execution Plans Internals — Reading the Optimizer's Mind

> **Core Concept**: Dissecting Physical Query Execution Plans  
> How relational engines process queries, and how to spot performance regressions before they hit production.

---

## 1. The Execution Plan: Declarative SQL to Physical Execution

SQL is a **declarative language**: you specify *what* data you want, not *how* to physically retrieve it.
The Execution Plan is the physical blueprint generated by the database engine detailing the exact sequence of data access operators, algorithms, joins, and memory allocations.

### The Volcano Iterator Model
Modern execution engines execute plans using the **Volcano Iterator Model**:
Every operator in the plan exposes three methods:
1. `Open()`: Initializes the operator and allocates state/buffers.
2. `GetNext()`: Returns the next single physical row (or vector batch) up the pipeline.
3. `Close()`: Tears down resources and releases memory.

Rows are pulled **from right to left, top to bottom**.

## 2. Fundamental Access Operators: Seek vs. Scan

```text
┌───────────────────────────────┐          ┌───────────────────────────────┐
│          INDEX SEEK           │          │          INDEX SCAN           │
├───────────────────────────────┤          ├───────────────────────────────┤
│ • B-Tree Navigation           │          │ • Sequential Leaf Navigation  │
│ • O(log N) Complexity         │          │ • O(N) Linear Complexity      │
│ • Reads only matching pages   │          │ • Reads EVERY page in index   │
│ • Optimal for selective OLTP  │          │ • Catastrophic for OLTP       │
└───────────────────────────────┘          └───────────────────────────────┘
```

### The Tipping Point
Why does the optimizer sometimes choose an **Index Scan** even when an index exists?
* **The Tipping Point**: The threshold where the optimizer decides that doing an Index Seek + Key Lookup is more expensive than simply scanning the entire clustered table sequentially.
* Usually occurs between **2% and 5% selectivity**. If a query matches more than ~3% of the rows in a table, an unindexed/non-covering index will trigger a full table scan!

## 3. The Dangerous Operators: Spotting Bottlenecks

### 1. Key Lookup (Bookmark Lookup)
```text
(Non-Clustered Index Seek) ──► [Key Lookup / Clustered Index] ──► (Output Rows)
```
* **What it means**: The query used a secondary non-clustered index to find matching rows, but the query requested columns that were **not included** in that index.
* **The Cost**: For every single matching row, the engine must navigate the Clustered Index B-Tree from root to leaf to retrieve the remaining columns (**Random I/O read amplification**).
* **The Fix**: Add the requested columns to the index using `INCLUDE (ColumnA, ColumnB)`.

---

### 2. Sort Operator & `tempdb` Spills
```text
[Stream of Rows] ──► [Sort Operator (Order By / Group By)] ──► [TempDB Spill]
```
* **The Mechanics**:
  - Sorting is a **blocking operator**: it cannot return its first row until it has consumed *all* input rows into memory.
  - The optimizer grants a fixed slice of query workspace memory based on its **Estimated Rows**.
* **The Catastrophe (Sort Spill Level 1 & Level 2)**:
  - If the optimizer estimates 100 rows, it grants 64 KB of memory.
  - If the query actually returns 500,000 rows (due to stale statistics or parameter sniffing), memory runs out!
  - The engine **spills the sorting buffers to physical disk (`tempdb` in SQL Server / workfile in PostgreSQL)**.
  - Query time explodes from **3 ms to 4,500 ms**!

### 3. Join Algorithms Comparison

| Operator | When the Optimizer Chooses It | Memory Cost | Strengths & Risks |
|---|---|---|---|
| **Nested Loops** | One small input (Outer) + Indexed lookup on Inner | **0 B (Streaming)** | Incredibly fast for OLTP; degrades to $O(N \times M)$ disaster if outer input is large. |
| **Merge Join** | Both inputs are already sorted on the join key | **0 B (Streaming)** | Highly efficient, linear $O(N + M)$ scan; requires pre-sorted data or an explicit sort step. |
| **Hash Match** | Large, unsorted, non-indexed datasets | **High (Build Hash Table)** | Builds an in-memory hash table of the smaller input; spills to disk if memory grant is exceeded. |

## 4. Sargability: The Silent Killer of Index Seeks

A query predicate is **Sargable** (Search ARGument ABLE) if the database engine can use it directly to perform a B-Tree binary search (Seek).

### Anti-Pattern 1: Wrapping Columns in Functions
```sql
-- NON-SARGABLE: Forces full Clustered Index Scan across 10 million rows!
SELECT OrderId, Total FROM Orders 
WHERE YEAR(CreatedAt) = 2026 AND MONTH(CreatedAt) = 8;

-- SARGABLE: B-Tree Index Seek between boundaries
SELECT OrderId, Total FROM Orders 
WHERE CreatedAt >= '2026-08-01' AND CreatedAt < '2026-09-01';
```

### Anti-Pattern 2: String Manipulations in WHERE
```sql
-- NON-SARGABLE: Evaluates UPPER() on every row in the table
SELECT Id, Email FROM Users WHERE UPPER(Email) = 'JOHN@EXAMPLE.COM';

-- SARGABLE: Case-insensitive collation or functional/computed column index
SELECT Id, Email FROM Users WHERE Email = 'john@example.com';
```

### Anti-Pattern 3: Implicit Data Type Conversions (`CONVERT_IMPLICIT`)
When passing parameters from .NET:
```csharp
// C# string defaults to NVARCHAR (Unicode: 2 bytes per char in SQL Server)
// If the DB column is VARCHAR (ANSI: 1 byte per char):
var user = await _context.Users
    .Where(u => u.NationalId == "123456789") // Generates: WHERE CONVERT_IMPLICIT(nvarchar, NationalId) = @p0
    .FirstOrDefaultAsync();
```
* Because the database must convert the column data type on every single row to match the parameter, **the index on `NationalId` is completely ignored**, causing a full scan!
* **The Fix**: Explicitly map column type in EF Core:
```csharp
builder.Property(u => u.NationalId).IsUnicode(false); // Forces VARCHAR in SQL
```

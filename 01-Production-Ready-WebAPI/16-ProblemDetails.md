# 16 - RFC 7807 & RFC 9457 Problem Details

> "An error contract is just as important as a success contract.
>
> When an API fails, it must fail with precision, standard machine-readability, and zero security leakage."

# Why Should a Principal Engineer Care?

In many organizations, every microservice invents its own custom error response schema:

### Team A (Payment Service):
```json
{ "success": false, "err_msg": "Card declined", "code": 402 }
```

### Team B (Order Service):
```json
{ "error": { "message": "Item out of stock", "details": ["Item 42"] } }
```

### Team C (Identity Service):
```json
{ "status": "FAILURE", "reason": "Token expired" }
```

This chaos forces client applications (Web, iOS, Android, third-party enterprise integrations) to write custom error-parsing adapters for every single endpoint.

As a Principal Engineer, you mandate a single, standardized, industry-wide specification: **RFC 7807 (updated by RFC 9457) Problem Details for HTTP APIs**.

# The Specification: RFC 7807 / RFC 9457

The IETF specification defines a standard JSON media type:

```http
Content-Type: application/problem+json
```

A Problem Details document contains five standard members:

```json
{
  "type": "https://api.novacommerce.com/errors/insufficient-funds",
  "title": "Insufficient Funds",
  "status": 400,
  "detail": "Your account balance of $45.00 is insufficient for order total of $120.00.",
  "instance": "/api/v1/orders/checkout",
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "errorCode": "ACC_INSUFFICIENT_FUNDS"
}
```

### Member Definitions:
- **`type` (string URI)**: A URI reference that identifies the problem type. When dereferenced in a browser, it should ideally provide human-readable documentation.
- **`title` (string)**: A short, human-readable summary of the problem type. It **must not change** from occurrence to occurrence (e.g., "Insufficient Funds", never "User 42 has only $5 left").
- **`status` (integer)**: The HTTP status code generated by the origin server. Must match the actual HTTP response status code.
- **`detail` (string)**: A human-readable explanation specific to this occurrence.
- **`instance` (string URI)**: A URI reference identifying the specific endpoint or resource where the problem occurred.
- **`extensions` (custom properties)**: Additional domain-specific fields (e.g. `traceId`, `errorCode`, `timestamp`, `errors`).

# Validation Errors: `ValidationProblemDetails`

For input validation failures (e.g. FluentValidation), the specification standardizes an `errors` extension member:

```json
{
  "type": "https://api.novacommerce.com/errors/validation-error",
  "title": "One or more validation errors occurred.",
  "status": 422,
  "detail": "See the errors field for details.",
  "instance": "/api/v1/customers",
  "traceId": "00-9a8b7c6d5e-01",
  "errors": {
    "Email": [
      "The Email field is not a valid e-mail address."
    ],
    "PostalCode": [
      "PostalCode must be 5 digits for US addresses.",
      "PostalCode is required."
    ]
  }
}
```

# Native Implementation in ASP.NET Core

Starting in .NET 7/8+, ASP.NET Core provides deep native support via `AddProblemDetails()`:

```csharp
builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = context =>
    {
        var httpContext = context.HttpContext;
        var problemDetails = context.ProblemDetails;

        // 1. Enrich with standard diagnostic trace ID
        problemDetails.Extensions["traceId"] = httpContext.TraceIdentifier;

        // 2. Add instance URI
        problemDetails.Instance = $"{httpContext.Request.Method} {httpContext.Request.Path}";

        // 3. Attach standard error classification code if available
        if (httpContext.Items.TryGetValue("ErrorCode", out var errorCode))
        {
            problemDetails.Extensions["errorCode"] = errorCode;
        }

        // 4. Attach timestamp
        problemDetails.Extensions["timestamp"] = DateTimeOffset.UtcNow;
    };
});
```

# Common Mistakes

❌ **Returning 200 OK with ProblemDetails in the Body**
```csharp
// ANTI-PATTERN: Breaks HTTP semantics and proxy caching
return Ok(new ProblemDetails { Status = 400, Title = "Bad Request" });
```
✅ **The HTTP response status code and `ProblemDetails.Status` MUST be identical.**

❌ **Putting Unique Occurrence Details into `Title`**
```json
{ "title": "Order ORD-991 failed because user 42 has $0" } // WRONG: Title should be static
```
✅ **Keep `Title` static and descriptive; put dynamic details in `Detail`:**
```json
{ "title": "Payment Failed", "detail": "Order ORD-991 failed due to insufficient funds." }
```

❌ **Leaking Stack Traces in Production `ProblemDetails`**
```csharp
// DANGEROUS: Exposes internal vulnerabilities to external clients
if (!app.Environment.IsDevelopment())
{
    // Ensure ExceptionHandler strips stack traces and internal exception messages before writing ProblemDetails.
}
```

# Architect's Decision

### Scenario
Nova Commerce needs an enterprise error standard across 20+ backend microservices consumed by web, mobile, and B2B vendor partners.

### Standard Adopted:
1. **Payload**: Strict compliance with RFC 7807 / RFC 9457 `application/problem+json`.
2. **Extensions**: Every error response must include:
   - `traceId` (W3C Trace Identifier)
   - `timestamp` (ISO 8601 UTC)
   - `errorCode` (Machine-readable enum string, e.g. `PAYMENT_GATEWAY_TIMEOUT`)
3. **Status Codes**: 
   - Syntactic errors: `400 Bad Request`
   - Semantic validation errors: `422 Unprocessable Entity`
   - Missing resources: `404 Not Found`
   - Concurrency conflicts: `409 Conflict`
   - Infrastructure faults: `500 Internal Server Error` (Sanitized)
